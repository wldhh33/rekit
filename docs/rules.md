# 分析口径与阈值

> 本文件第 0 节是**通用口径**，适用于所有分析器；第 1 节起是 triage 的判据与阈值。

## 0. 通用口径

### 0.1 `.text` 内搜索必须声明边界类型

> **任何在 `.text` 内做搜索的结论，必须声明是基于指令边界还是字节扫描；
> 字节扫描得到的命中必须显式标注可能落在操作数内部。**

- **指令边界**：命中来自 `funcs` 的递归下降指令流（`discover(..., insn_out=...)`），
  地址一定是某条已解码指令的起点。`rekit xref` 的确定集属于这一类。
- **字节扫描**：按字节/字长在可执行节里匹配。命中可能落在立即数、位移或
  指令中段，**不能**当作“某条指令引用了它”。`rekit xref --byte-scan` 的结果
  全部标 `suspected`，并在 `detail` 里写明“可能命中操作数内部”。
- 输出/汇报里必须写清是哪一种；两种混在一起时，必须分开列，不得合并计数。

违反这条会重现 M3 的失步坑：用线性字节扫描代替指令流，得到看似命中、
实际落在操作数中间的假引用。

### 0.2 元数据当线索，不当结论

站点标签、节名、文件大小、编译器声明都只是线索；结论必须来自实测
（熵、`unpack`、解析结果）。典型例子：M3-02 的 goCrackMe 站点标 “Packer”，
实测熵与 `unpack` 均不支持，因此记 `packed=false`，标签留在 `note` 里。

### 0.3 位移当绝对地址前，先看段前缀

> **任何把操作数位移当绝对地址的解释，必须先确认无段前缀；带 `fs:`/`gs:` 的
> 访问是线程局部或系统结构，不是镜像内地址。**

- `fs:[0]`（64 位 TLS；32 位 PE 上同一写法是 SEH 链）、`fs:[0x28]`（Linux canary）、
  `gs:[0x10]` / `gs:[0x30]` / `gs:[0x60]`（Windows TEB/PEB）里的 `disp`
  是相对 FS/GS 基址的偏移，**不能**当成 `[disp]` 绝对内存。
- 触发它的真实 bug：`clang_O0` 的 77 条 `fs:[0]` 被 `xref` 记成绝对引用，
  目标 0 又恰好落在非 alloc 的 `.comment` 节里，于是产出 77 条假引用；
  同一轮排查还发现 `jmp rdx` 的 `op.imm` 回落到寄存器枚举值 `RDX=0x28`，
  被误判成 `jmp 0x28`。两者都是“把操作数里的数字直接当目标”。
- 已按此口径修 `xref`（`abs-mem` 要求 `segment == 0`）、`funcs` 的冷启动
  取值（三处绝对槽位）、`data` 的结构体字段偏移统计（`segment == 0`）。
- 反之，**带段前缀的 RIP 相对**（`fs:[rip+disp]`）仍按 RIP 规则判定：
  段前缀只否决“绝对地址”这一条路径，不否决正常路径。

### 0.4 “常量搜索未命中”不等于“常量不存在”

> **`--const` / `--string` 的 0 命中只能说明“没有原样出现”，不能推出“不存在”。
> 编译器可以拆分、异或、移位、或跨字节重叠构造常量。**

- 典型：M3-08 的 7 字节口令比较被折成 `cmp r8, 7` + `mov ecx, 0x48555648` + `mov edx, 0x4e444148`
  + 两次 `xor` + `or`；两个 dword 在偏移 3 处重叠。字面量 `0x140038EE0` 的 xref 命中为 0，
  但比较确实存在（`0x140001FD6`）。
- 另一个方向：M3-10 的 key0=4 由 `0x80070057 → xor ax,dx → rol eax,4 → shr ax,1` 生成，
  文件里根本找不到字节 `04` 作为该常量。
- 因此：**断言“常量不存在”时，必须补一条说明**——搜索范围（节/偏移窗口）、搜索方式（等值/掩码）、
  以及是否检查过同函数内的立即数运算；缺这条说明的结论一律降级为“未找到”。
- 该规则只管“结论怎么表述”，不代表已具备常量重组能力；重组搜索的可行性见
  `计划/M4-运行时与壳识别设计.md` §6，未实现前不得据此下判定。

### 0.5 加壳样本的数据目录是“壳后镜像”的，不是原件的

> **加壳样本里 `.reloc` / Load Config 目录非零，不代表能读出原件的重定位表或
> Guard 字段；目录项、结构体、字段值三层都可能只描述壳，或只是原件的过期副本。
> 未做交叉核对前，一律报 `packed-unknown`，不得输出具体字段当结论。**

2026-11-13 在 4 个 UPX 5.0 PE32+ 样本上实测到三种形态（证据
`实践/2026-11-13-upx-chain/residue.csv`）：

| 形态 | 实例 | 照读会得到 | 为什么错 |
|---|---|---|---|
| 清零 | 7z / hello_go 的 `.reloc`，7z 的 Load Config | “无重定位 / 无 CFG”（假阴性） | 原件分别有 880 / 7,762 项重定位，值与镜像一起被压走 |
| 最小重建表 | hello_rs `.reloc` 12 项、notepad 10 项（原件 304 / 366） | “整个镜像只有 12 个地址需要重定位” | 表确实描述**壳后镜像**（12 个 qword 都是 `0x1400xxxxx` 真 VA），但描述的不是原程序 |
| 原件副本 | hello_rs Load Config 与原件逐字段同值（`GuardFlags=0x100`、check=`0x1400172F8`）；notepad 的 `GuardFlags` 被改成 `0x800`（原件 `0x417500`） | “CFG 已插桩 / 未插桩” | 字段是原件的或壳改写过的；`check` 指向的地址在壳后落在压缩流内 |

三条必查判据（任一命中即不可用）：

1. 目录 RVA 落在 `SizeOfRawData == 0` 的节（UPX0），或落在压缩节 UPX1 的原始字节区；
2. 与同源未加壳文件配对比对字段（没有配对就只能报未知，不能猜）；
3. `.reloc` 条目数远小于同规模未加壳样本，或条目指向的页落在压缩流内
   （hello_rs 的页 `0x24000` 在原件表里不存在）。

工具侧：`工具库/pe/cfg_guard_scan.py` 对加壳样本只出 `packed-unknown`；
`--no-code` 用于“只看头与 Load Config”的场景，判定写 `no-code`，避免拿残留字段凑结论。

### 0.6 UPX method=14 是“2 字节自有 props + 裸 LZMA1”；原重定位表必须先剔 ABS 再对照

> **method=14 的压缩流不是 LZMA-alone：开头只有 2 字节 UPX 自有 properties
> （`pb = b0 & 7`、`lp = b1 >> 4`、`lc = b1 & 15`），随后直接是 LZMA1 流，
> 没有 5 字节属性头、没有 8 字节 size、没有 EOS marker。
> 把首字节当 LZMA-alone 属性解释会得 `lc = 0x1a % 9 = 8`（非法），这是此格式解码全败的根因。**

- 依据：`样本/tools/upx-src/upx-5.0.0/src/compress/compress_lzma.cpp:358-360,416-434`
  与两套 stub 的 `lzma_d.S`（同样只跳 2 字节）。
- 校验：`lc<9`、`lp<5`、`pb<5` 且 `lc+lp<=4`；越界必须报错，不得静默换解码器。
- 判定：裸 LZMA1 没有结束标记，“消费字节数”不可验证；只按 PackHeader 的 `u_len`
  与 adler 判定。实测 `--lzma` 产物：141,660 B，adler `0x959BC30F`，`.text` 与原件 0 字节差。

重定位恢复：`rebuildRelocs` 从 `orig_crelocs` 重放原表，壳后最小表**不参与**恢复
（它只描述壳后镜像，见 §0.5）。与原 `.reloc` 对照时，两侧都按**写出的字节**解析：

| 样本 | 原表项数 | 其中 ABS(type 0) | 重建对照 |
|---|---|---|---|
| hello_rs | 304 | 5 | 304/304 逐项相等（含 5 条 ABS 填充） |
| notepad | 366 | 2 | 366/366 逐项相等（含 2 条 ABS 填充） |

ABS 条目是块对齐填充（每块 `8 + 2n` 字节需补到 4 字节对齐），原件有，重建侧
`_reloc_block` 同样会补——**对照必须比“写出的字节表”**。只比逻辑位置列表会漏掉填充项，
误报“少 5 条 / 少 2 条”。运行时 rebase 是否实际执行仍未确证，不得写成“运行时重定位已还原”。

工具侧：`rekit unpack` 的检查项「解压」与「重定位表对照」（有同源原件时才出）；
`tests/test_upx_chain.py` 钉住 props `(3,0,2)`、非法 props 报错、LZMA/NRV2B 产物逐字节相同。

# triage 判据与阈值

- 适用版本：rekit 0.1.0
- 来源：学习项目资产 **PE-007**（`工具库/pe/pe_anomaly.py`）+ 3 组 UPX 加壳/未加壳配对实测
- 改这里必须同步改 `rekit/analyzers/triage.py` 的常量与 `tests/test_triage.py`

---

## 1. 信号表

| ID | 权重 | 判据 | 证据字段 | 为什么 |
|---|---|---|---|---|
| `S1_upx_section_pair` | +4 | 同时存在 `UPX0` 与 `UPX1` | 节表 FO + 节名列表 | UPX 默认外观；改名即可绕过，故不给高分 |
| `S2_upx_section_any` | +2 | 命中 UPX 类节名但未成对 | 节名列表 | 残缺/变种，单独不足以定案 |
| `S3_zero_raw_exec_section` | +3 | `VirtualSize>0` 且 `RawSize=0` 且 `MEM_EXECUTE` | 节头 FO + VirtualSize | 磁盘无内容、内存是解压区；加壳的强特征 |
| `S4_high_entropy_section` | +2 | 任一 `RawSize>=4096` 的节熵 > 7.8 | 节名 + 熵值 | 压缩/加密数据；单独也可能是压缩资源 |
| `S5_import_truncated` | +3 | DLL ≥ 3 且 函数数/DLL < 2.0 | 导入目录 RVA + 计数 | UPX 5 保留 DLL 名但截断函数表（一 DLL 一函数） |
| `S6_import_empty` | +1 | 导入函数数 = 0 | 计数 | **仅参考**：静态链接的 Go/Rust 也可能为空 |

置信度：`≥9 高 / 5–8 中 / 2–4 低 / <2 无`。

判定映射：`UPX0+UPX1 成对 → upx`；`score≥5 → packed?`；`score≥2 → odd`；否则 `normal`。

---

## 2. 阈值从哪来（实测）

样本：`hello_rs.exe`（未加壳，130560 B）与 `hello_rs.packed.exe`（UPX 5.0.0 `--best`，62976 B），均为自编译 Rust Hello World。

| 指标 | 未加壳 | 加壳 | 阈值取法 |
|---|---|---|---|
| 节数 | 5（`.text .rdata .data .pdata .reloc`） | 3（`UPX0 UPX1 UPX2`） | 节名直接判 |
| 最高熵 | 6.436 `.text` | 7.888 `UPX1` | 7.8 落在两者之间，且 >7.8 的节基本只剩压缩数据 |
| 导入 函数/DLL | 85/10 = 8.5 | 13/10 = 1.3 | 2.0 落在两者之间 |
| 零 Raw 可执行节 | 无 | `UPX0`（VS=0x15000，RS=0） | 布尔判据 |

`MIN_ENTROPY_SECTION=4096` 的作用：排除几百字节的小节（随机性导致熵虚高）。

`MIN_DLLS_FOR_RATIO=3` 的作用：只有 1–2 个 DLL 的小程序，比值天然低，不能作为加壳证据。

## 3. 误报边界（已知会被骗过）

| 情形 | 结果 | 说明 |
|---|---|---|
| 改节名的 UPX（`UPX0/UPX1` → 随意名） | 6 分/中 | S1、S2 失效，只剩 S3+S4+S5 |
| Themida / VMProtect / Enigma | 可能 0–2 分 | 保留完整导入表，S5 不触发；S3 视实现而定 |
| ASPack / PECompact / MPRESS | 视节名 | S1/S2 只认 `UPX` 前缀 |
| NSIS / Inno 安装器 | 低分 | 只有高熵，S4 单独不计结论 |
| .NET 单文件 bundle | 低分 | 同上 |
| 静态链接 Go/Rust（未加壳） | 可能触发 S6（+1） | 单独 1 分 → 置信度「无」，符合预期 |
| 把压缩数据塞进 `.rsrc` | 可能触发 S4 | 需结合资源树判断，v0.2 后再补 |

**一句话**：triage 只回答「要不要继续深挖」，不回答「有没有恶意」。
