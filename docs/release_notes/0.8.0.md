# rekit 0.8.0 — x86（PE32）支持

**性质**：功能新增（minor）。`schema_version` 与族语义不变（仍为 0.7 的 schema 3），
x64 的行为、门限与历史数字一律未动。

## 这版加了什么

- **x86（PE32）解析**：自研解析层在 SysWOW64 抽样 200 个文件上与 pefile 2024.8.26
  逐字段比对 —— 194 个 PE32 的头字段（1,746 项）、节字段（6,000 项）、RVA 探针（3,165 项）
  **0 差异**；另 6 个 16 位 NE 文件双方一致拒绝。
- **scope 标注**：x86 输出 `bitness=x86`、`scope=out_of_m4a`，**不冒充 x64**、
  **不进 M4a 的 x64 计分**；x86 结果单列，不与 x64 合并、不报 macro。
- **x86 `funcs`（B 层函数发现）**：无权威表时的入口 / 指针表 / 间接调用 / 穷举路径。
- **明确不做 x86 库函数识别**：没有签名库匹配，不标注、不剔除已知库函数。

## 召回：两个数必须一起看

单样本 `notepad_x86`，参照表 = Ghidra 的 613 个函数（排除 thunk / external）：

| 口径 | 数值 | 说明 |
|---|---:|---|
| **对参照表全表** | **69.2%（424/613）** | **对外应报这个**，回答「能找到多少」 |
| 可达闭包内 | 98.2%（267/272） | 只说明「直接 `call`/`jmp` 闭包内不漏」 |
| 独立闭包对照 | 98.1%（265/270） | 同上，换 Ghidra 引用图做边 |

- 98.2% / 98.1% 的分母是「从入口沿直接 `call`/`jmp` 走得到的闭包」，
  **一个会跟直接调用的工具天然接近满分，不能当作能力结论**。
- 两条闭包口径重合 269/270（99.6%），**不构成独立性检验**：换边来源后结论不变，
  说明它不是某个实现的特异现象，但两者测的是同一件事。
- **x86 没有权威表**：参照表是 Ghidra 的函数划分，只能同层横向自比，
  不能当绝对真值，也不能与 x64 的数字并列、求差或画趋势。

## 已知问题（保留原值，不为好看重算）

- 可达子集 R 允许 `ret` 之后的尾部 `jmp` 构成边，而块遍历走不到不可达尾部。
  这个不对称让 **98.2% 偏低**（去掉这类边后分母 271、命中 267 = 98.5%），
  并使 3 个未命中属于「分母定义缺口」而非能力缺口。按冻结口径保留。
- 缺口中的 5 例（`0x40A2EC`、`0x426304`、`0x426C13`、`0x426C63`、`0x426D22`）
  原样记录，不重算。

## 其他修复

- **identify 的 `msvc` 反向约束**：linker 14.x 若同时呈 MinGW/LLD 形态（无 Rich 头、
  全小写含 `.buildid`/`.note` 的节名、CRT 仅 `api-ms-win-crt-*`、内嵌 `mingw` 三元组），
  `T16` 单信号不得硬判 `msvc`，转 `unknown` 并写明依据。
- **`basis` 改为由实际命中信号拼接**（信号 id + 偏移 + 实测值），不再写固定文案。
- **快照基线机械重建**为 `tests/baseline/snapshot_v0.8.0.json`：逐键比对差异只有
  `version`（90 处）与 meta 日期，无契约字段变化。
