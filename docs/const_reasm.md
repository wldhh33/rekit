## 2. 结果

| 门槛 | 实测 | 判定 |
|---|---|---|
| 已知 ≥2/3 且 08 必中 | **3/3**，08 字节完全一致（重叠位 `H` 一致） | 通过 |

对照集为什么退化（如实记）：SHA256 排序后第一个文件是 `winrnr.dll`（156 个函数），
满足「无大立即数」的函数全是 1–42 条指令的桩/小函数，检测器结构上不会在它们上面产生 hint。
因此「0 误报」只说明**没机会误报**，不说明判别力。这是协议判据本身的局限，不是检测器干净。

## 3. 判定与后果

- **不接入，且本线关闭**：不新增 `--hint-const`，不输出 `suspected_constant`；不写进 `identify` 的
  `family / verdict / confidence`；不改 M3/M4 的任何准确率口径。
- 实现代码**已从 rekit 包中移除**，归档到 `实践/2026-11-12-reasm/const_reasm.py`
  （与评估脚本同目录）；**不进发布包、不参与构建，rekit 内无任何调用方**
  （`grep -r const_reasm rekit/` 只命中本文件），不得被 CLI/analyzers 引用，也不再做性能优化。
- **不再尝试**（2026-11-12）：v1、v2 两轮都未同时满足门槛；v2 跨文件分层后对照集仍 0 hint，
  且 3/30 个真实二进制耗时 4–11 s。v1 里「若将来要再试……」的设想作废，不再按该方向续做。
- **归因限制（第 3 条门槛不能用于证明「常量重组成本不可接受」）**：3/30 不合格里最大的
  `UpdateAgent.dll` 10.913 s，成本主项是**函数发现本身**（6,621 个函数 / 735,237 条指令的
  `funcs` 遍历），不是常量重组。因此第 3 条门槛实际测出来的是「大 DLL 上 `funcs` 发现慢」，
  与常量重组无关；大 DLL 函数发现性能已单列为一条待办（`计划/待办-大DLL函数发现性能.md`），
  不随本线关闭一起埋掉。
- 若要重启，只能作为**新课题另立设计**（新评估框架、新供给、新验收），不得沿用本文件的
  门槛与样本，也不得把它算作本线的「第三轮」。
